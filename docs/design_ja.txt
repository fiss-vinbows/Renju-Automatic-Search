Rapfi ログ読み取り・自動操作アプリ 開発計画
作成日：2026年9月11日
改訂日：2026年9月13日（認識方式を画像認識からログ読み取りへ変更）

0. 改訂の要点
・Rapfi（YixinBoard）は settings.txt の「record debug log」を 1 にすると、GUI とエンジン（engine.exe）の全通信を debuglog.txt に書き出す。
・盤面の交点に表示される百分率・L系・W系は、このログ中の候補手ごとの評価情報（INFO PV ブロック）から生成されている。
・したがって、文字列画像のOCRは行わず、debuglog.txt を読み取って判定する。OCRに起因する誤読・検出漏れ・判読不能の問題は解消される。
・分岐①の判定条件を「百分率が0件」から「すべての候補手の評価値が -M で始まる」に変更する。
・判定には EVAL（評価値）のみを用い、WINRATE（勝率）は参照しない。
  EVAL が整数の候補手は評価値が未確定（探索継続中）、±M 表記の候補手は勝敗が確定した読み切りである。
・操作は Rapfi のコマンド入力欄（ログ下のテキスト欄）へのコマンド送信で行う。ボタンや盤面交点のクリックは不要になる。
  停止 = thinking stop、戻る = undo one、防御 = searchdefend、マルチPV = nbest 2、着手 = putpos（現在の手順＋選んだ手）。
・探索の役割：負け側（守る側）の探索は searchdefend（状態A）、勝ち側（攻める側）の探索は nbest 2（状態B）。
  状態遷移で戻る回数を誤ると手番と探索の種類が食い違うため、各分岐の戻り先を第5・6項のとおり定める。
・時間条件・戻る回数などの数値はすべて設定ファイル monitor_config.json で変更できる。GUI（RapfiAuto.exe）からも編集できる。
・分岐⑤（2026-09-18 追加）：どちらの手番でも「最善手以外の候補がすべて -M」なら最善手を着手し、その次の手から探索を続ける。
  負け側で成立 → 着手後は勝ち側の手番なので nbest。勝ち側で成立 → 着手後は負け側の手番なので searchdefend。
・自動探索モードは GUI のトグルスイッチでオン／オフする。監視中に人が Rapfi を操作（thinking stop 等）した場合は自動的にオフになる。
・探索モード（2026-09-18 追加）：「nbest探索あり」= defend探索側（searchdefend）と nbest探索側（nbest 2）を交互に行う現行仕様。
  「nbest探索なし」= 双方とも searchdefend。探索時間は1つの設定（defend_mode_seconds）を共通で使う。
  nbest探索なしモードで +M を検出したら「直前の相手の手が悪手」として1手戻して searchdefend（nbest探索側の扱いと同じ）。
・四への即応（2026-09-18 追加）：手番側が相手の四を止めるしかない局面（相手が次に五を作れる空点がちょうど1つ、かつ自分に五がない）では、
  探索せずにその止め手を着手する。着手を伴う操作の後に応手が連鎖する場合は、まとめて1回の putpos で送る。
・呼び名：本書の「負け側／勝ち側」「分岐①〜⑤」は設計説明用の名前であり、アプリ上では「defend探索側／nbest探索側」、
  「全候補が負け」「最善手を着手」「勝ち筋を検出」「探索時間終了」「最善手以外が負け」「四を検知」と表記する。

1. 目的と対象範囲
Rapfiのエンジンログ（debuglog.txt）を読み取り、候補手の評価内容と経過時間に応じて、停止・戻る・防御・マルチPV・着手の各操作をコマンド入力欄から送信する。
最初の防御は人が押し、その後は状態Aと状態Bを自動で循環する。
本書は設計・開発の計画である。ログ読み取り（parse_debuglog.py）、監視（monitor.py）、コマンド送信部（sender.py）は実装済み。
2026-09-18 に自動送信モード（monitor.py --auto）で分岐①～④を含む複数周回の自動運転を実環境確認済み（短縮時間）。
残りは第5段階（本来の1時間／30分での長時間評価）。

2. 読み取る情報
ログ中の候補手1件は次の並びで記録される。
  INFO PV n → INFO DEPTH / SELDEPTH / NODES / EVAL / WINRATE / BESTLINE → INFO PV DONE
このうち次を利用する。
・EVAL（評価値）：整数（例「637」「-562」）、または読み切り表記「+M14」「-M14」。
  整数は評価値が未確定（探索継続中）であることを表す。±M は勝敗が確定した読み切りであり、数字は決着までの手数である。
・WINRATE（勝率）：0～1の小数。GUIは百分率表示に使うが、本アプリの判定には用いない。
・BESTLINE（読み筋）：先頭の座標がその候補手の位置。座標は「行,列」で0始まり、行は上から数える（例「2,12」= M13）。
・DEPTH / SELDEPTH（深さ／選択深さ）。

盤面表示との対応：
・百分率（例「10%」「13%」）：EVAL が整数の候補手（評価値未確定）。本アプリでは表示値ではなく EVAL の整数を比較に用いる。
・L系（例「L58」）：EVAL が「-M数字」の候補手（自分が数字手で負け）。
・W系（例「W43」）：EVAL が「+M数字」の候補手（自分が数字手で勝ち）。
各候補手には、種別、EVAL原文、EVAL の整数値（整数の場合）、格子位置（列文字＋行番号）、深さ、取得時刻を保持する。
EVAL の大小は文字列順ではなく整数として比較する。
色情報は使用しない（ログには含まれない）。

ログにはこのほか、GUIが送った現在局面（yxboard または yxquerydatabaseallt に続く「行,列[,色]」の並びと done）、
画面の「深さ | 値 | 時間 | 読み筋」行（MESSAGE Depth …）、マルチPV各行（MESSAGE (n) …）が含まれる。
局面の手順は「いま監視している解析がどの局面のものか」の識別に使う。

3. 要件の解釈と実装前の確認事項
次の事項は仕様が確定していないため、実画面・実ログの確認時に決定する。
（1）確認済み：Windows 標準 API（user32）で Yixin ウィンドウを前面化し、校正済みのウィンドウ相対位置をクリックして入力欄にフォーカスを与え、
     文字列＋Enter を SendInput で送る（src/sender.py）。追加ライブラリ不要。ウィンドウサイズが校正時と異なる場合は送信せず再校正を求める。
     バックグラウンド動作：前面化せずにキーを届ける方式（PostMessage / SendMessage）は GTK が非アクティブ時のキー入力を受け付けず不可（2026-09-18 確認）。
     代替として、送信の瞬間（約0.5秒）だけ Yixin を前面化し、送信後に直前の前面ウィンドウへ戻す。送信は分岐成立時のみなので他の作業への影響は小さい。
     ただし送信中にユーザーがキー入力していると混入し得るため、送信直前に前面が Yixin であることを確認し、違えば送らない。
（2）格子の行列数（putpos の手順生成に必要。座標変換は第8項(5)）。
（3）各コマンド送信後のログ変化（2026-09-13 に全コマンド確認済み。第9項の表を参照）。
     確認済み：コマンド入力欄や toolbar から実行したコマンドは「EXECUTE_COMMAND : コマンド」の行として記録される。これを受付確認に用いる。
     確認済み（2026-09-13）：undo one は解析中なら自動で yxstop を送った後、yxblockreset に続いて1手短い局面が送り直される。
     確認済み：echo / sleep は GUI 内で処理されエンジンに送られないため、ログには記録されない（自前の目印をログに埋め込む用途には使えない）。
（4）ログ上で「解析が完了した」「解析中である」をどう判別するか。
     暫定方針：MESSAGE Depth 行または INFO PV DONE の出現から一定時間新着がなければ「確定」とみなす。
     yxstop 送信後に届く最後の INFO PV DONE 群を「停止直前の確定結果」とする。
（5）最大評価値の選択対象が、直前の確定結果か、それまでの履歴全体か。
     暫定方針：「停止直前の最新の確定結果」に含まれる整数 EVAL の候補手を比較する。
     過去の解析で出て消えた候補手や、過去の最大値は選ばない。
（6）最大値が同値で複数ある場合の選択順。
     暫定方針：上の行を優先し、同じ行では左を優先する。
（7）評価値の範囲。
     EVAL は整数または ±M数字であることを実ログで確認済み。それ以外の形式は「不明」として扱う。
（8）確認済み：putpos は局面を設定するだけで解析は始まらない。続く nbest 2 が解析を開始するため、thinking start は不要。
     確認済み：thinking start はエンジンに board を送り「エンジンが着手する」対局用コマンドである。自動操作アプリでは使用しない。
（9）人が最初に防御を押してから状態Aのログ（INFO PV ブロック）が現れるまでの遅延。
（10）+M（W系）が一瞬だけ記録されることがあるか。
     ログは追記型で消えないため、一度でも +M が記録されれば検出できる。「表示時間が短くて見逃す」問題は生じない。
（11）ログの追記タイミングとバッファリング。
     GUI がファイルへ書き出す遅延を実測し、監視間隔を決める。
（12）ログの肥大化。実測で約30MB/時間（約0.7GB/日）増え続け、Rapfiを終了するまで減らない。
     確認済み：Rapfiは追記モードで書いているため、起動中にファイルを0バイトに切り詰めても次の書き込みは先頭から正常に始まる（2026-09-13 実機確認）。
     暫定方針：監視アプリが追記分のみを読む方式とし、一定サイズ（設定値、目安50MB）を超えたら必要に応じて退避してから切り詰める。切り詰め後は読み取り位置を先頭に戻す。

4. 状態と時間の基本方針
状態は「開始待ち」「状態A監視」「状態B監視」「操作中」「異常一時停止」「終了」に分ける。
Rapfiの「停止（thinking stop）」と、自動操作アプリ側の「一時停止／緊急停止」は別の機能とする。
状態Aの制限時間は3,600秒、状態Bは1,800秒を既定とし、設定ファイル（monitor_config.json の a_limit_seconds / b_limit_seconds）で変更できる。
経過時間の計測には、時計の時刻変更に影響されにくい単調増加時計を用いる。
各状態への移行ごとにタイマーを初期化し、停止・戻るなどの遷移操作時間は次状態の監視時間に含めない。

開始方法：
・ユーザーが自動操作アプリを「開始待ち」にしてから、Rapfiの防御を手動で押す。
・防御操作はログに yxsearchdefend として記録されるため、その行の出現時刻を開始時刻として記録する。
・自動防御／マルチPV操作では操作時刻を記録し、対応するログ（yxsearchdefend / yxnbest）と後続の INFO PV ブロックの出現を確認してから、その時刻を基準として監視する。
  期待するログが現れなければ、監視を開始せず異常一時停止する。

5. 状態Aの判定と動作
状態Aでは、候補手の EVAL を監視する。

分岐①：開始から1時間未満で、すべての候補手の評価値が -M で始まった。
判定条件：
・最新の確定結果に候補手が1件以上存在する。
・その全候補手の EVAL が「-M数字」である（評価値未確定の整数 EVAL の候補手が0件＝全候補手が負けの読み切り）。
・EVAL が「+M数字」の候補手や、形式を解釈できない候補手が存在しない。
・ログの読み取りが正常であり、監視中の局面の手順が変化していない。
・上記を複数回の読み取りで安定確認する（解析途中で一時的に全候補が -M になる場合を除外する）。
  実装：INFO PV の周回（pv_index の巻き戻り）を単位に「条件を満たした周回数」を数え（既定3周回）、
  かつ状態A開始から最低経過時間（既定10秒）を過ぎていること。実機では searchdefend 直後の1秒以内に
  複数周回が完了することがあり、周回数だけでは浅い探索の一時的な結果を除外できない（2026-09-18 確認）。
ログの新着がない状態や、INFO PV ブロックが途中までしか書かれていない状態を①と判定しない。
実行順：thinking stop → undo one（目標手数になるまで繰り返す）→ searchdefend → 状態A監視。
意味：負け側が n手の局面で n+1 手目を探索中に全候補が -M になったら、n-1 手目の探索（n-2 手の局面）に戻し、負け側の探索をやり直す。
戻り先は設定 undo_offset_branch1（既定 -2 = 停止前の手数−2）。
確認済み（2026-09-13）：thinking stop はエンジンが読んでいた最善手を盤面に打つため、停止直後は n+1 手になる。
そのため undo one は通常3回（n+1 → n → n-1 → n-2）だが、回数ではなく「局面の手数が n-2 になるまで」で制御する。
各回の完了確認は、GUIが送り直す局面の手数が1減ることをログで確認する。目標より短くなったら異常一時停止する。

分岐⑤（負け側）：最善手（整数 EVAL の候補）が1件だけで、他の候補がすべて -M。
判定条件：①と同じ安定確認（周回数＋最低経過秒数）を課す。+M の候補がある場合は⑤ではなく異常一時停止（状態Aで +M は想定外）。
実行順：thinking stop → putpos（現在の手順＋最善手）→ nbest 2 → 状態B監視。
意味：負け側の応手が事実上1つしかないので、その手を打ち、勝ち側の探索へ進む。

分岐②：開始から1時間経過した時点で、EVAL が整数（評価値未確定）の候補手が1件以上残っている。
実行順：
1）停止直前の確定結果（候補手一覧）をJSONで保存する。
2）その一覧のうち EVAL が整数の候補手について整数値を比較し、最大値の格子位置（列文字＋行番号）を保存する。±M の候補手は比較対象に含めない。
3）thinking stop を送り、ログに yxstop が記録され、以後 INFO PV ブロックが増えないことを確認する。
4）現在の手順に最大値の格子位置を追加した putpos コマンドを送り、局面が1手進んだことをログで確認する。
5）nbest 2 を送る。
6）状態Bへの移行を確認し、状態B監視を開始する。
最大値を確定できない場合や、putpos 後の局面がログで確認できない場合は、推測して次の操作を送らず異常一時停止する。

6. 状態Bの判定と動作
マルチPV操作後、ログに yxnbest が記録され、続いて候補手が2～3件（設定値）の INFO PV ブロックが繰り返し出力されることを状態B確認の基本とする。
移行確認の具体条件は実ログで調整する。

分岐③：開始から30分未満で、EVAL が「+M数字」の候補手（W系）を少なくとも1件検出した。
実行順：thinking stop → undo one（②で着手する前の局面＝停止前の手数−1 になるまで。通常2回）→ searchdefend → 状態A監視。
意味：勝ち側に勝ち筋（+M）が見つかった＝②で着手した負け側の手が悪手。その手を打つ前の局面に戻して負け側の探索をやり直す。
エンジンはその手が負けであることを学習済みのため、次の②では別の候補が選ばれる（同じ局面の往復を避ける）。
戻り先は設定 undo_offset_branch3（既定 -1）。
評価値が大きいだけの候補手（EVAL が整数）はW系に含めない。

分岐⑤（勝ち側）：+M の候補がなく、最善手（整数 EVAL の候補）が1件だけで、他の候補がすべて -M。
判定条件：③（+M）を先に判定し、+M がない場合にのみ⑤を判定する。安定確認は①と同じ。
実行順：thinking stop → putpos（現在の手順＋最善手）→ searchdefend → 状態A監視。
意味：勝ち側の手が事実上1つしかないので、その手を打ち、負け側の探索へ進む。

分岐④：開始から30分経過しても、「+M数字」の候補手が記録されない。
実行順：thinking stop → searchdefend → 状態A監視（戻さない）。
意味：勝ち側が制限時間内に勝ち筋を見つけられなかった＝②の着手は有効。thinking stop でエンジンが盤面に打つ勝ち側の最善手を
そのまま採用し、その次の負け側の手番で searchdefend に入って前進する。
（以前の「1手戻して防御」は勝ち側の手番で searchdefend してしまう誤りだった。2026-09-18 修正）
戻り先は設定 undo_offset_branch4（既定 null = 戻さない）。
③と④の操作処理は共通化し、ログには「W検出」「30分経過」の理由を区別して残す。
ログの読み取りが継続的に失敗している場合や、ログの新着が長時間ない場合は「Wなし」と断定しない。

7. 境界時刻と未定義状態
・①と③は、安定確認が完了した時刻が期限より前の場合に成立とする。
・期限ちょうどでは時間到達側の判定を優先する。
・状態Aで期限に達したら最新の確定結果を取得して②を判定する。
・期限時点で整数 EVAL の候補手がなく全候補が -M の場合（①の安定確認が期限前に終わらなかった場合）は、
  -M は読み切り結果なので安定確認を待たずに①（戻る）として扱う（2026-09-18 変更。以前は一時停止していたが、
  短い探索時間では深い探索の1周回に10秒以上かかり、安定確認が間に合わないことがあった）。
  整数も -M もない（解釈できない候補のみ）場合に限り一時停止する。
・defend探索側（状態A）で「+M数字」の候補手が現れた場合は、直前の nbest探索側の手（thinking stop でエンジンが打った手など）が悪手であることを意味するため、
  異常ではなく「1手戻して nbest探索をやり直す」（nbest探索側で +M が出た場合と対称。2026-09-20 変更）。
・解釈できない評価値が出るなど、本当に想定外の内容は異常一時停止の対象とする。
・スリープや長時間の読み取り中断後は、経過時間だけを理由に操作せず、ログと画面を再確認して再開判断を求める。

8. ログ読み取りの設計
（1）ログの有効化と場所
初回設定で settings.txt の「record debug log」を 1 にする（Rapfi停止中に変更する）。
debuglog.txt は Rapfi のフォルダ直下に生成され、起動ごとに「----------new record----------」から書き直される。

（2）行の形式
各行は「SEND_COMMAND [時計情報]: 本文」（GUI→エンジン）または「RECEIVE_COMMAND [時計情報]: 本文」（エンジン→GUI）である。
本文の末尾に空白や改行コード（CR）が付くことがあるため、必ず除去してから解釈する。

（3）ストリーム解析
ファイルを先頭から読まず、監視開始時点のオフセットから追記分だけを逐次読む。
INFO PV n から INFO PV DONE までを1件の候補手として組み立て、途中の状態で判定に使わない。
SEND の yxboard / yxquerydatabaseallt に続く座標列と done を現在局面として保持し、局面が変わったら候補手一覧を初期化する。
同じ局面が繰り返し送られる（データベース問い合わせのため）ので、手順が同一なら初期化しない。

（4）候補手一覧の確定
候補手は格子位置をキーにして最新の INFO PV ブロックで上書きする（深い探索結果ほど後に来る）。
「確定結果」は、一定時間（設定値、目安0.5～1秒）新着がない時点の一覧、または yxstop 後に届いた最後の一覧とする。

（5）座標変換
ログ座標「行,列」（0始まり、行は上から）を、列文字（A～O）＋行番号（15－行）に変換する。
putpos に渡す手順は、この表記を小文字で連結したもの（例 h8h9j10i9）とする。

（6）異常の管理
形式を解釈できない行は「不明」として保持し、件数を記録する。
「読み取り結果がない」ことを「候補手がない」ことと同一視しない。
Rapfi の再起動（new record 行の出現）、ファイルの消失、長時間の新着なしを検知したら異常一時停止する。

（7）監視間隔
初期設定の目安は0.2～0.5秒間隔の読み取り、2～3回の安定確認とする。
ログは追記型なので短時間の表示を見逃す問題はなく、間隔は判定遅延と負荷の兼ね合いで決める。

9. 操作制御の設計
操作はすべて Rapfi のコマンド入力欄へのコマンド送信（文字入力＋Enter）で行う。
利用するコマンド（Yixin のコマンドリストより）：
  thinking stop … 停止
  undo one … 戻る（1手）    searchdefend … 防御（解析を開始する）
  nbest [2,3,...] … マルチPV（解析を開始する）   putpos [手順] … 局面設定（解析は開始しない）
  使用禁止：thinking start（エンジンが着手する対局用コマンド）。echo / sleep はログに残らないため使わない。
操作は必ず1本のキューで順番に実行し、監視ループからの重複発火を防ぐ。
各操作は「対象ウィンドウと入力欄の確認 → コマンド送信 → EXECUTE_COMMAND 行による受付確認 → 期待するログ変化の確認」の単位で実行する。
  thinking stop：EXECUTE_COMMAND : thinking stop → yxstop の記録と INFO PV ブロックの停止。
                 続けてエンジンの最善手が盤面に打たれ、1手長い局面が送り直される（防御・マルチPVの両モードで確認済み）。
  undo one：EXECUTE_COMMAND : undo one →（解析中なら yxstop）→ yxblockreset → 1手短い局面の送り直し。
  searchdefend：EXECUTE_COMMAND : searchdefend → yxsearchdefend → INFO PV ブロックの開始。
  nbest 2：EXECUTE_COMMAND : nbest 2 → start 15 / yxboard / yxnbest 2 → NUMPV 2 の INFO PV ブロックの開始。
  putpos：EXECUTE_COMMAND : putpos … → 空の yxboard → 指定手順の yxboard。解析は始まらない。
固定の待ち時間だけに依存せず、ログ変化を待つ。
コマンドの効果が不明な場合、特に undo one を無条件に再送しない。
再試行はログから未実行と確認できる場合に限定し、確認不能なら一時停止する。
入力欄がフォーカスを失っている、ウィンドウが最小化されている、対象アプリが終了している場合は送信しない。
undo one は1回送るごとに EXECUTE_COMMAND : undo one の記録を待ってから次を送る（局面の送り直しは重複して届くため、
これをしないと送りすぎて目標手数を通り過ぎる。2026-09-18 に実機で発生・修正済み）。
監視状態（状態A／B）の間に人がコマンドを実行した場合（help / echo を除く）は状態が食い違うため、自動探索モードをオフにする（GUI のトグルが自動で戻る）。
キー入力の送信先を誤ると他のアプリに文字が入るため、送信直前に前面ウィンドウが Rapfi であることを必ず確認する。
将来、コマンド入力欄を経由せずに Rapfi へコマンドを渡せる方法（標準入力、ホットキー定義 function/hotkey*.txt）が見つかれば置き換える。

10. 自動操作アプリの構成
・ログ読み取り部：debuglog.txt の追記を逐次読み、行を解釈する。
・解析部：INFO PV ブロックを候補手として組み立て、種別（百分率／L系／W系／不明）を判定し、局面を追跡する。
・送信部：Rapfi ウィンドウを確認し、コマンド入力欄に文字列と Enter を送る。
・状態管理部：状態、経過時間、判定結果、遷移理由を保持する。
・操作部：コマンド列の組み立て、送信部への依頼、送信後のログ確認を行う。
・設定画面（GUI、src/gui.py、tkinter）：探索時間などの設定編集と保存、自動探索モードのトグルスイッチ、状態・残り時間・候補手要約・ログの表示、
  入力欄の校正、debuglog.txt の切り詰め。見た目は games.html（ダーク基調、アクセント #63e6be、丸いトグル）に合わせる。
  トグルをオンにした時点で Rapfi がすでに searchdefend / nbest 中なら、ログ末尾からその状態を推定して途中から監視に入る。
・配布形態：PyInstaller で単一 exe（RapfiAuto.exe）。Rapfi フォルダ直下のサブフォルダ RapfiAuto\ に、monitor_config.json / sender_config.json と共に置く。
  debuglog.txt は親フォルダ（Rapfi フォルダ）から読む。Rapfi 本体のファイルと混在させない。
・記録部：時刻、候補手一覧、操作、エラーを保存する。

Windowsを対象とし、試作はPythonとする。ログ解析は src/parse_debuglog.py を基礎とし、キー入力送信の部品を交換できる構造にする。
OCRおよび画像認識ライブラリは不要とする。画面情報は前面ウィンドウの確認にのみ用いる。

11. 記録と復旧
各分岐の成立時、停止直前、コマンド送信直前、異常時に候補手一覧（JSON）と送信したコマンドを保存する。
状態A／Bの開始時刻、経過時間、分岐番号、最大評価値の候補一覧と選択位置を記録する。
debuglog.txt 自体の容量上限を設定し、超過時は退避してから切り詰める（Rapfi起動中でも可。第3項(12)参照）。
再起動後に途中のコマンド手順を自動再開せず、現在のログを確認して開始位置を決める。
緊急停止を受けたら未実行の入力を破棄し、以後の入力を停止する。
自動操作アプリの一時停止中にRapfi側も停止するかは、別設定として仕様を確定する。

12. 開発の進め方と成果物
第1段階：ログ・コマンド仕様の確認
状態A、状態B、①～④の直前、各コマンド送信後のログを収集する。
百分率のみ、-Mのみ、+M混在、解析途中、局面変更直後を含むログを用意する。
成果物：確定要件、ログ形式一覧、操作順と完了条件、解析用サンプルログ。

第2段階：解析のみの試作（実施済み・継続）
保存したログを入力して、局面と候補手一覧（種別・評価値・格子位置）を表示する確認機能を作る。
→ src/parse_debuglog.py として実装済み。追記監視（--follow）の実環境確認と、確定判定・種別判定の追加が残る。
成果物：解析試作、判定精度の確認結果。

第3段階：コマンドを送らない監視試作
実ログを監視し、「①成立」「最大値 J7（637）を選択予定」などの予定動作を記録する。
時間条件は設定で短縮できるようにし、実待機をせず状態遷移を検証する。
成果物：状態管理、タイマー、判定ログ。

第4段階：操作の実装
thinking stop、undo one×3、searchdefend、putpos、nbest 2 の順に個別動作を検証し、各コマンドのログ上の完了確認を実装する。
ログ確認・重複操作防止・緊急停止を組み込んでから連続運転する。
成果物：操作機能付き試作。

第5段階：統合・長時間評価
短縮時間で全分岐を試し、その後に本来の1時間／30分で動作を確認する。
複数サイクルの運転で、ログ肥大化、タイマーずれ、記録容量、操作失敗を確認する。
成果物：評価報告、設定済みアプリ、起動・停止・復旧手順書。

13. 主な検証項目と受け入れ基準
・①：期限前に全候補手が -M になったとき、停止 → 局面が停止前より2手短くなるまで戻る → 防御 が指定順に実行される。
・②：期限後に整数 EVAL の候補手が残ったとき、最新の確定結果の最大評価値の手を putpos で着手し、nbest 2 へ進む。
・③：期限前の +M を検出し、停止・防御へ進む。
・④：+M なしで期限に達したとき、停止・防御へ進む。
・EVAL「-562」「637」「1200」などを整数として大小比較でき、±M は比較対象から除外される。
・同値最大、複数の +M、解析途中の一時的な全 -M、局面変更直後を正しく扱う。
・ログ新着なし、ファイル消失、途中までのブロックで①を誤発火しない。
・putpos 後の局面がログで確認できなければ、次のコマンドを送らない。
・期限直前、期限ちょうど、期限直後の判定が第7項に従う。
・undo one の途中失敗、コマンド無反応、フォーカス喪失、スリープ復帰で余分な入力を行わない。
・緊急停止後に新しい入力を送らない。
・評価用ログでの分岐誤発火と最大値選択ミスが0件であることを初期受け入れ条件とする。

14. 実装着手に必要な情報
最初に、状態A／Bの代表ログ、各コマンド送信後のログ変化、コマンド入力欄へのキー入力送信の可否を確認する。
続いて、第3項の未確定事項（特に（4）確定判定と（11）追記遅延）を確定し、第3段階の監視試作へ進む。
コマンド送信とログ確認の方法が確認できた時点で、自動操作を含む実装の規模と工期を見積もる。
